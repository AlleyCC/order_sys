# order-data-scope Specification

## Purpose

定義訂單、帳戶餘額與交易紀錄查詢的資料可見範圍:訂單清單只用於「發現可跟的團」而僅回開放中訂單的摘要,誰訂了什麼與帳戶金額只有當事人或參與者看得到,需要跨使用者檢視的後台職能(客服處理爭議、會計對帳)改走獨立的唯讀端點,使「看得到誰的資料」成為可授權、可撤銷的權限。

## Requirements

### Requirement: 訂單列表只回開放中訂單的摘要

一般訂單列表查詢的用途是讓使用者**發現可以參與的團**,因此 SHALL 回傳所有開放中(OPEN)的訂單,不以呼叫者是否參與為條件——否則尚未參與的使用者無從得知有哪些團可跟,也就永遠無法參與。

回覆 MUST 只包含摘要欄位(訂單識別、名稱、截止時間、低消金額);MUST NOT 包含參與者、品項或任何金額歸屬資訊——那些屬於訂單明細,僅參與者可讀。分頁的總筆數 MUST 只計入開放中的訂單。

#### Scenario: 未參與任何訂單的使用者仍看得到可跟的團

- **WHEN** 一位未發起也未在任何訂單中下單的使用者查詢訂單列表,系統中存在開放中的訂單
- **THEN** 回覆包含該開放中訂單,使其得以進一步查詢並參與

#### Scenario: 非開放中的訂單不出現

- **WHEN** 使用者查詢訂單列表,系統中同時存在開放中、已結算與已取消的訂單
- **THEN** 回覆只包含開放中的訂單,總筆數亦只計入開放中的訂單

#### Scenario: 清單不洩漏參與者與品項

- **WHEN** 使用者查詢訂單列表
- **THEN** 每筆訂單只帶摘要欄位,不含參與者名單、品項明細或任何人的金額

### Requirement: 訂單明細僅參與者可讀

訂單明細查詢 SHALL 僅允許該訂單的參與者(發起者或曾在其中下單者)讀取;非參與者 MUST 收到 HTTP 403,且回覆 MUST NOT 洩漏該訂單的任何內容。

訂單不存在時 MUST 回覆與「非參與者」完全相同的狀態碼與訊息:若兩者可區分,任何人都能以一串識別碼試出系統中存在哪些訂單(存在性洩漏)。

#### Scenario: 參與者讀取訂單明細

- **WHEN** 訂單的發起者或下單者查詢該訂單明細
- **THEN** 回覆完整明細(品項、參與者、狀態)

#### Scenario: 非參與者讀取訂單明細被拒

- **WHEN** 與該訂單無關的已登入使用者查詢該訂單明細
- **THEN** 系統回覆 HTTP 403,回覆中不含該訂單的任何欄位

#### Scenario: 不存在的訂單與無權限的訂單無法區分

- **WHEN** 使用者以一個不存在的訂單識別碼查詢明細,以及以一個存在但與其無關的訂單識別碼查詢明細
- **THEN** 兩次回覆的狀態碼與錯誤訊息完全相同,無法藉此判斷哪一個訂單真實存在

### Requirement: 帳戶餘額查詢僅限本人

帳戶餘額查詢 SHALL 以呼叫者的身份憑證決定查詢對象。若請求帶有指定使用者的參數,系統 MUST 忽略該參數,MUST NOT 依其回傳他人餘額。

#### Scenario: 查詢自己的餘額

- **WHEN** 已登入使用者查詢帳戶餘額
- **THEN** 回覆該使用者本人的餘額與可用餘額

#### Scenario: 指定他人參數不生效

- **WHEN** 已登入使用者查詢帳戶餘額,並在請求中指定另一位使用者
- **THEN** 回覆仍為呼叫者本人的餘額,不回傳被指定者的任何金額

### Requirement: 交易紀錄查詢僅限本人

一般交易紀錄查詢 SHALL 只回傳呼叫者本人的交易紀錄。

#### Scenario: 查詢自己的交易紀錄

- **WHEN** 已登入使用者查詢交易紀錄
- **THEN** 回覆僅含該使用者本人的紀錄

### Requirement: 指定不存在的使用者須明確回報

以使用者為查詢對象的交易紀錄查詢,當該使用者不存在時 SHALL 回覆 HTTP 404,MUST NOT 回覆空清單——對帳作業無法區分「查無此人」與「此人沒有交易」,會把輸入錯誤誤判為業務事實。

#### Scenario: 對帳時打錯使用者識別碼

- **WHEN** 具備會計角色的使用者以一個不存在的使用者識別碼查詢後台交易紀錄
- **THEN** 系統回覆 HTTP 404,而非 200 與空清單

### Requirement: 後台唯讀端點提供全系統資料

系統 SHALL 提供獨立於一般查詢的後台唯讀端點,供需要跨使用者檢視的職能使用:全系統訂單查詢(供客服處理爭議)與任一使用者交易紀錄查詢(供會計對帳)。這些端點 MUST 登記為受管制資源,由角色權限決定誰能呼叫;它們 MUST 為唯讀,MUST NOT 提供任何資料異動能力。

#### Scenario: 客服查詢全系統訂單

- **WHEN** 擁有客服角色的使用者呼叫後台訂單查詢端點
- **THEN** 回覆不受呼叫者參與範圍限制的訂單資料

#### Scenario: 會計查詢任一使用者的交易紀錄

- **WHEN** 擁有會計角色的使用者呼叫後台交易紀錄查詢端點並指定某使用者
- **THEN** 回覆該使用者的交易紀錄

#### Scenario: 無授權角色呼叫後台端點被拒

- **WHEN** 不具備對應角色的已登入使用者呼叫後台訂單或交易紀錄查詢端點
- **THEN** 系統回覆 HTTP 403

#### Scenario: 撤銷角色後後台端點立即不可用

- **WHEN** 管理員移除某使用者的客服角色,該使用者持原憑證(仍在有效期內)再次呼叫後台訂單查詢端點
- **THEN** 系統回覆 HTTP 403
