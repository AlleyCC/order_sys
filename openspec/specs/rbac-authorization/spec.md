# rbac-authorization Specification

## Purpose

定義每次 API 請求的身份驗證與動態授權行為:系統如何辨識「這個人是誰」與「他能做什麼」,包含 401/403 語意區分、免登入白名單、權限查詢的快取行為與快取故障時的降級策略。

## Requirements

### Requirement: 每次請求皆須驗證身份

系統 SHALL 在每一次受保護 API 請求時驗證呼叫者身份,不得只在登入時驗證一次後完全信任。身份憑證僅用於證明「你是誰」,不作為權限判斷的依據。

#### Scenario: 持有效憑證的請求

- **WHEN** 使用者以登入取得的有效憑證呼叫受保護 API
- **THEN** 系統識別出該使用者的身份,請求進入授權判斷

#### Scenario: 無憑證的請求被擋下

- **WHEN** 使用者未附任何憑證呼叫受保護 API
- **THEN** 系統回覆 HTTP 401,錯誤訊息明確表達「未登入」語意
- **AND** 不執行任何業務邏輯

#### Scenario: 過期或無效憑證的請求被擋下

- **WHEN** 使用者附上已過期或簽章無效的憑證呼叫受保護 API
- **THEN** 系統回覆 HTTP 401,與「無憑證」相同語意

### Requirement: 依角色權限動態授權

系統 SHALL 於每次請求時,依「該使用者目前擁有的角色」與「角色被授權的資源(API URL pattern + HTTP method)」判斷是否放行。授權規則 MUST 來自資料庫(可能經快取),不得寫死於程式碼,調整後 MUST 即時生效(不重啟服務、不要求重新登入)。

#### Scenario: 有權限的操作成功

- **WHEN** 角色「行政」被允許「建立分類」,且擁有行政角色的使用者以有效憑證呼叫該功能
- **THEN** 操作成功

#### Scenario: 無權限的操作被拒絕

- **WHEN** 角色「行政」未被允許「調整使用者角色」,且僅擁有行政角色的使用者呼叫該功能
- **THEN** 系統回覆 HTTP 403,錯誤訊息明確表達「權限不足」(而非「未登入」)
- **AND** 沒有任何資料被異動

#### Scenario: 未登記於資源表的受保護端點

- **WHEN** 已登入使用者呼叫一個未在資源表登記的受保護端點
- **THEN** 請求放行(維持「登入即可存取」的既有行為);僅登記於資源表的端點才受角色權限管制

### Requirement: 一帳號可擁有多個角色

系統 SHALL 支援一個帳號同時擁有多個角色;該帳號的有效權限為其所有角色權限之聯集。

#### Scenario: 任一角色具備權限即放行

- **WHEN** 使用者同時擁有「客服」與「行政」角色,且僅「行政」被允許「建立分類」
- **THEN** 該使用者呼叫「建立分類」成功

### Requirement: 未登入與權限不足回覆不同語意

系統 SHALL 對「未登入(401)」與「已登入但權限不足(403)」回覆不同的 HTTP 狀態碼與可區分的 JSON 錯誤內容,使前端能分別處理。

#### Scenario: 兩種拒絕可被前端區分

- **WHEN** 未登入的請求與已登入但無權限的請求分別被拒絕
- **THEN** 前者收到 401 與「未登入」語意的 JSON,後者收到 403 與「權限不足」語意的 JSON,兩者格式一致但語意可區分

### Requirement: 白名單端點免登入

系統 SHALL 提供集中設定的白名單機制;白名單內的端點(登入、token 換發、API 文件頁等)MUST 可在未登入狀態下存取。

#### Scenario: 未登入存取白名單端點成功

- **WHEN** 未登入使用者存取登入端點或 API 文件頁
- **THEN** 請求成功,不被身份驗證擋下

### Requirement: 權限查詢使用快取降低資料庫壓力

系統 SHALL 快取「使用者→角色」與「角色→資源」查詢結果,重複請求不重複查詢資料庫。快取 MUST 支援精準失效:權限異動時僅使受影響的快取條目失效,下次查詢時自資料庫重建。

#### Scenario: 重複請求命中快取

- **WHEN** 同一使用者於快取有效期間內連續呼叫多次受保護 API
- **THEN** 角色與權限資料自快取讀取,不重複查詢資料庫

#### Scenario: 快取失效後自動重建

- **WHEN** 某角色的權限快取被失效(如管理員調整權限)後,該角色的使用者再次發出請求
- **THEN** 系統自資料庫讀取最新權限並重建快取,請求依最新權限判斷

### Requirement: 快取故障時授權降級不中斷

WHEN 快取服務不可用,系統 SHALL 直接自資料庫讀取角色與權限資料完成授權判斷;登入與授權功能 MUST NOT 因快取故障而完全停止運作。

#### Scenario: 快取服務故障時操作仍成功

- **WHEN** 快取服務不可用,且一個已登入且有權限的使用者呼叫正常應成功的功能
- **THEN** 操作仍然成功(系統改以資料庫取得權限資訊),不會直接整體失敗

### Requirement: 角色表僅收錄系統職能角色

`roles` 表 SHALL 只收錄「全系統有效、由管理員指派、跟人走」的職能角色(判準:這個身分能不能寫在員工名冊上)。訂單週期內產生的身分——團長(開團者)與團員(下單者)——MUST NOT 以角色形式存在;此類身分一律由訂單資料本身判斷。系統 MUST 允許使用者不擁有任何角色,零角色為合法且常態的狀態。

#### Scenario: 開團者身分不來自角色

- **WHEN** 任一已登入使用者建立一筆團購訂單
- **THEN** 建立成功,且系統不因此指派任何角色給該使用者
- **AND** 該使用者對這筆訂單的管理權限,依其為該訂單的開團者判斷,與其擁有的角色無關

#### Scenario: 零角色使用者可使用未受管制端點

- **WHEN** 一位不擁有任何角色的已登入使用者呼叫未登記於資源表的端點(如開團、下單、查詢自己的資料)
- **THEN** 請求放行

#### Scenario: 零角色使用者呼叫受管制端點被拒

- **WHEN** 一位不擁有任何角色的已登入使用者呼叫已登記於資源表的端點
- **THEN** 系統回覆 HTTP 403

### Requirement: 跨 ownership 的救援操作依系統角色判斷

部分業務操作允許非資料擁有者執行(客服處理爭議時取消他人發起的團購訂單、刪除他人的品項)。此類跨 ownership 的操作 SHALL 依呼叫者當下的系統角色判斷,MUST NOT 依身份憑證內的任何內容判斷;角色被撤銷後,同一份憑證的下一次請求 MUST 立即失去該能力。

#### Scenario: 客服取消他人發起的團購訂單

- **WHEN** 擁有客服角色的使用者取消一筆由他人發起、狀態為 OPEN 的團購訂單
- **THEN** 訂單狀態變更為 CANCELLED,結算排程一併移除

#### Scenario: 客服刪除他人的品項

- **WHEN** 擁有客服角色的使用者刪除一筆他人下在他人團中的品項
- **THEN** 刪除成功,並通知該品項所屬使用者其可用餘額已變動

#### Scenario: 無相關角色者不得跨 ownership 操作

- **WHEN** 既非開團者、亦不具備客服或超級管理員角色的使用者,嘗試取消他人發起的團購訂單
- **THEN** 系統回覆 HTTP 403,且訂單狀態未變更

#### Scenario: 撤銷客服角色後救援能力立即消失

- **WHEN** 管理員移除某使用者的客服角色,該使用者持原憑證(仍在有效期內)再次嘗試取消他人的團購訂單
- **THEN** 系統回覆 HTTP 403
